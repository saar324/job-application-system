## Current state and measured unknowns

`worker/automation.js` already normalizes case and punctuation for common profile labels, fills files/selects/radios, detects Next/Continue, and builds a final preview. It loops over live controls and fills as it describes them. A required unknown field returns `needs_input` immediately, before later pages can be inspected. The preview records intended fills from each step, not a verified readback of every visible value; older step values may no longer be available in the DOM. Its map key is only field key plus label, so a repeated control on a later step can replace an earlier review entry. Each field summary clips text to 240 characters and `src/service.js` clips the owner-facing approval message to 3,500 characters, so approval may omit material content. The generic action detector is text based and gives final-submit buttons priority. It has a 16-transition bound and fixed 250/750 ms sleeps. The optional `worker/adaptive.js` fallback requests one model action per observation and has no job/company evidence packet. `src/discovery/service.js` accepts source IDs and a per-source limit, then scores results; it has no filter-discovery or query-plan contract. Greenhouse, Lever, and Ashby feed adapters exist, while board/site selections are configured privately. The installed skill mandates a fresh application sub-agent per role, while this repository's skill describes bounded recurring cycles. No repository evidence currently proves which of these costs dominates the reported eight hours.

The `job-application-system` repository is the newer design with SQLite, MCP, telemetry, and adaptive execution. The separate `job-application-server` repository and installed skill may still be used elsewhere. A local `jobctl health` attempt on 2026-09-21 reached no service at `127.0.0.1:4310`; this does not establish production deployment status.

## Single-lane workflow

One coordinator owns discovery and a bounded queue. One reusable application agent handles one application at a time. The server keeps durable status, preview, approvals, answers, and receipts. The agent receives a small job packet by ID, finishes or checkpoints it, then receives the next ID. Keep per-job model calls stateless or summarize them to bounded context; a long chat does not literally erase prior tokens. A blocked application yields its lane and can be resumed from server state. Never depend on chat memory or a live browser tab for recovery. Keep one external application tab open at most. The server worker uses a fresh browser context for each attempt and closes it on return; visible browser handoff is a separate client path.

The initial implementation should keep server browser execution serial for the owner's profile even if the global worker can serve other profiles. Do not implement or enable same-profile parallelism as part of this change. Replace the skill's fresh-sub-agent-per-application instruction only when batch-agent checkpoint and context-reset tests pass.

## Field inventory and answer plan

Use a versioned `FormStep`/`Field` schema. Extract ordinary native controls in a small number of DOM evaluations per step, including accessible label, associated label, name, ID, placeholder, autocomplete, type, required state, current value, options, radio/checkbox group, section heading, visibility, enabled state, constraints, and an attempt-local locator. Handle ARIA widgets, frames, and contenteditable controls through typed adapter extensions; a single page DOM evaluation cannot span all frames. Inspect frames individually with Playwright frame locators when allowed by browser policy, including cross-origin frames that Playwright can access. Mark denied or inaccessible frames as unresolved. Preserve CSS-hidden native file inputs that are activated by a visible upload control. Do not read hidden applicant data into model context.

Future steps cannot generally be known before clicking Next. Inventory all fields on the current step, prepare and validate them, advance only through a classified non-final transition, then inventory the next step. Official ATS form metadata may seed a provisional full-form inventory, but browser observations remain authoritative. A step signature combines origin, normalized route, control structure, and progress indicator. Maintain a visited-signature set and a transition budget so loops are detected without losing legitimate DOM-only steps.

Resolve common fields through an explicit alias registry rather than broad substring matching. Normalize Unicode/case/spacing; require the field type and surrounding semantics to agree. `email`, `first/given name`, `last/family/surname`, full name, phone, location, address, portfolio, LinkedIn, GitHub, résumé/CV, and verified reusable answers are candidate mappings. A name field must not absorb a company name; an email field must not map to a referral email. Ambiguous matches become unresolved. Approved reusable answers need scope and provenance: exact or equivalent question meaning, jurisdiction, employer/role if relevant, owner confirmation, and expiry or review date. A generic prior “Yes” must never answer a different country's work-authorization question. Migrate legacy scalar `applicationAnswers` conservatively rather than assuming global reuse. Validate against browser field validity and known constraints, including URL scheme, select membership, maxlength, and staged-file identity; avoid a restrictive custom email regex. Never fabricate a value to satisfy validation. Store provenance as profile field, approved answer ID, job evidence ID, or approved generated text ID; redact secrets in review artifacts.

`AnswerPlan` contains every observed field, normalized candidate value, source, decision reason, sensitivity, validation result, and intended action. Deterministic answers do not need a separate LLM review by default; they do need mechanical validation and live readback. The final machine check covers deterministic and model-written answers together in every approval mode. New original prose is flagged for owner review unless it matches an already approved reusable answer. A batch may collect exact prepared reviews for one consolidated approval under existing policy: the approval request lists each application ID, company, role, and complete-preview fingerprint, and the server records an approval for only those exact entries. It cannot authorize later or changed applications. Unknown factual, legal, work-authorization, compensation, demographic, or identity questions require owner input under existing policy. Optional open text may be left blank when appropriate. Only eligible original-prose questions go to the model.

## Bounded prose drafting

The API prepares a minimal `ApplicationEvidencePacket` before dispatch from the canonical listing/source, verified applicant experience and portfolio excerpts, approved reusable answers, and writing style. It excludes credentials, unrelated profile sections, and entire résumé files. Before any drafting, the coordinator checks the existing employer exclusion catalog and any explicit application instruction about AI assistance or human-only authorship; a prohibition stops autonomous drafting/submission and becomes a human handoff. The worker inventories the current step, sends only eligible prose questions with exact text/limits and selected evidence IDs to a constrained `DraftProvider`, and remains in the same browser attempt for the response. This is a model call within the worker protocol, not a new application sub-agent or general browser-control loop. Page text is untrusted as instructions to the agent, but employer application rules are policy evidence to classify and honor.

If a company-specific question needs material absent from the packet, the worker returns a typed `needs_research` result rather than browsing arbitrary sites or guessing. This requires a new explicit webhook-adapter/service transition to `waiting_research` with no owner confirmation. The coordinator obtains bounded official company material, records URL/content hash and freshness, extends the packet, and requeues the application in a fresh browser context with a bounded research/replay count. Cache only public company material. This extra replay is acceptable for genuinely missing evidence and should be measured. The draft call must fit within the worker's existing 180-second webhook deadline and its own stricter budget. A **received** typed worker response can certify that a draft timeout occurred before any final action; a lost response, server restart, or worker crash cannot. In those cases, retain uncertain-outcome manual review unless a separately designed durable phase protocol proves no final action began. Do not infer pre-submit safety from the server's current `submitting` status or a client-side timeout: that status is set before browser execution starts, and the HTTP deadline can expire after a final click. The worker currently does not cancel execution when the HTTP client gives up, so a timed-out attempt may still be active and may later persist a receipt. Before any retry, fence the application, establish that the old worker attempt has ended, reconcile its durable receipt store and the employer site, and only then clear uncertainty. Add a worker attempt-status/reconciliation contract for this; until it exists, keep the application in manual review and do not enable an automatic timeout retry. The model returns typed JSON keyed by field ID with draft, evidence IDs, and an `insufficient_evidence` outcome. The worker validates shape, length, field binding, evidence references, and obvious unsupported numbers or named claims. Mechanical checks cannot prove that natural-language claims are true, which is why new prose receives exact owner review. It cannot turn a draft into a verified personal fact. One optional revision call may resolve a concrete validator failure; otherwise ask the owner. Do not send unrelated applicant data or credentials to the model.

## Apply, verify, and recover

Fill from the plan in bounded batches within the current page generation. Re-resolve locators and stop on a DOM generation change. After filling, read actual control values and option labels from the page, compare to the plan, inspect native validity plus inline and summary errors, and inventory any newly shown conditional fields. Record both intended and observed values. The canonical approval artifact includes all full observed answers, every field/step, document filename and staged-file identity, role identity, form origin, and policy/schema version. Do not clip a value before hashing or owner review. Long reviews must be split into numbered parts or opened as a complete private review artifact; the owner must have access to every field before approving. For an earlier step that is no longer visible, retain its verified readback and step signature, and invalidate the whole approval if any step is revisited and changed. Stable role/form identity should be used in the fingerprint; volatile session query parameters should not cause false mismatches.

Classify actions as `start`, `non_final_next`, `review_step`, or `final_submit` within the active application form using button role, form context, URL/progress evidence, and adapter knowledge. Ambiguous Submit/Continue labels or multiple competing actions stop for review; the presence of a Submit control elsewhere on the page must not override Next. A non-final click waits for navigation, popup, form-generation change, or validation errors within the attempt deadline, with a short bounded fallback. If validation blocks progress, re-inventory the same step and repair only fields for which an authoritative answer exists. Never interpret a failed Next click as final submission. After explicit final approval of the exact cumulative preview, revalidate live values and fingerprint immediately before final click. If final-click validation explicitly rejects the form before any submission side effect, re-inventory, repair, and require a new complete review; a server error is safe to retry only when it reliably states that no application was created. A click otherwise remains an uncertain outcome until reliable new success evidence and a persisted receipt exist; generic success words plus an unrelated body change are insufficient. Never blindly retry after an ambiguous final click.

Keep an in-attempt checkpoint at each step: application ID, step signature/index, field inventory hash, answer-plan version, verified field summaries, unresolved owner questions, destination origin, and attempt boundary. Add a versioned checkpoint to the worker's typed `needs_input`, `needs_research`, and `needs_human` responses and propagate it through the webhook adapter into server storage before the state transition completes; the current `NeedsInputError`/`NeedsReviewError` and `#needsInput` paths carry requirements only. Persist it at owner-input, final-approval, challenge, research, or manual-review boundaries. Validate its size and shape and keep it private. Persisting progress before every browser action would require a new worker-to-server progress protocol and is a separate optional reliability change. Store no password, cookies, raw document, or model prompt in the checkpoint. On the next attempt, the worker opens a fresh context at the application URL and re-inspects/replays safe pre-submit steps; prior locator IDs and ephemeral session state are invalid. If the form cannot be reconstructed, hand off for manual review rather than claiming to resume the abandoned page.

## Source-query catalog

Each source adapter exposes `describe()` with source ID, version, capability type (`official_feed`, `public_board`, `browser`), allowed filters and enum values, whether each filter is pushed to the provider or applied locally, pagination/sort, geographic caveats, rate/crawl policy, freshness, and failure modes. The agent sends a typed bounded `SearchPlan` containing one or more queries, source, mode, filter values, result limit, and a scan-cycle idempotency key. The service validates against enabled sources and configured boards, coalesces repeated board-wide fetches across queries, executes only the needed provider requests, normalizes results, deduplicates canonical role IDs, applies eligibility/scoring, and returns compact items plus provenance and diagnostics. A repeated key within the same scan cycle returns the same durable result; a later cycle can refresh the source. Provider filters that require exact enum spelling, such as Lever's case-sensitive categories, use discovered values from a recent feed or configured values. It must never accept arbitrary URLs, scripts, selectors, unconfigured employer boards, or unrestricted site queries from the agent.

For Greenhouse, Ashby, Lever, and Himalayas, keep discovery on documented public listing APIs. Lever and Himalayas document useful server-side filters; Ashby's lightweight feed is board-wide, so requested role filters are local. Ashby results marked `isListed: false` are excluded from autonomous discovery but remain eligible for an owner-supplied direct URL. Fetch Greenhouse application questions only for shortlisted roles; those fields are provisional because the live form can differ. Lever's public Postings API does not expose custom application questions; its application POST API requires an employer key. No generic direct-submit API is assumed. For browser-only sources, use a source adapter with known UI controls and bounded waits; honor site access rules, source attribution requirements, backoff on 429/challenges, and stop rather than trying to evade blocks. LinkedIn remains user-controlled under the existing skill rule. Track adapter version, failure reason, yield per request, success rate, and last validated fixture. A single maintenance agent may repair a broken adapter after the active application is checkpointed; fixture and policy review precede re-enabling it.

## Browser-tool decision

Keep the existing Playwright library inside the isolated worker as the first production choice: it already supplies fresh contexts, locators, actionability waits, file uploads, network policy, and receipt capture. Test Playwright CLI for agent-led development/fixture exploration because its concise commands may reduce agent context. Test Playwright MCP when rich accessibility introspection is useful; do not expose unrestricted browser tools to the production application agent. Stagehand and Browser Use are candidates only for isolated unsupported-form pilots. Stagehand v3 can run a local browser but AI methods still call a configured model; any cloud cache/recording must be disabled or explicitly approved for private form data. Both candidates must pass the same action-policy, privacy, latency, and receipt gates. Codex Chrome/in-app browser is useful for visible owner handoff, not the system's durable execution boundary. Headless versus headed mode is an operational choice to benchmark, not a fix for repeated reasoning. No library is adopted on claims of speed alone.

## Measurement and rollout

Instrument a trace per application with timings for source fetch, normalization, screening, queue, browser launch, load, inventory, deterministic planning, model research/draft, fill, readback, each transition, approval wait, final submit, and receipt verification. Count tool calls, model calls/input/output tokens, pages, fields, retries, validation errors, challenges, and worker restarts. Attribute coordinator-agent tokens when its runtime exposes usage; mark them unavailable otherwise rather than reporting zero. Report p50/p95 active time for all started applications and separately for verified, blocked, and failed outcomes; report total elapsed time and source yield per hour. Never log answer values or full page content. The reported 100/8h is anecdotal, not a baseline for causal attribution.

Benchmark at least 30 anonymized form fixtures spanning the supported ATSs, custom forms, multi-step/conditional flows, errors, and challenges. Use a small screening subset for alternative browser tools, then run finalists on the full corpus using the same role packets, hardware, network constraints, and approval simulation. Synthetic receipts measure parser correctness; a separate owner-approved live pilot measures real receipt and site compatibility. Record time, tokens, correct fill rate, manual handoff, and verified receipt rate by outcome. Audit the deployed path and add instrumentation first, while fixing complete approval review, action classification, and receipt evidence before enabling any speed feature. Then run shadow plans, deterministic readback, prose drafting, source queries, and reusable agent sessions. Each feature has an independent flag and rollback path. Do not promote a faster path if correctness or receipt evidence regresses.
