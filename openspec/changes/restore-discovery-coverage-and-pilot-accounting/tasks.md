### Partial implementation notes

- The title gate now recognizes configured software-role spelling and AI/ML equivalents and hard-excludes explicit unrelated occupations even when the description mentions relevant skills. It does not broaden automatic eligibility beyond the existing score, pay, geography, and skill gates. A paired scorer comparison on the frozen 100-case holdout and 30-case development set found no selection changes; suitable-role recall remained 11/26 and 6/9 respectively. Those historical rows did not exercise the new variants, so dedicated fixtures cover them and the broader retrieval/prose release gate in 4.0c remains open.
- Himalayas' official API documentation defines `country` as an eligibility filter for a resident, with worldwide matches included unless `exclude_worldwide` is set. Its current adapter leaves that exclusion unset, so the residence-country query does not by itself prove an overly narrow geography search there. The other browser sources remain unaudited under 1.5.
- The browser catalog contained narrow legacy entry URLs. The branch supports a bounded rotation of privately configured, reviewed same-origin HTTPS listing URLs instead of embedding applicant-specific source choices in public code. Two paced browser shadows each took 35 seconds/nine requests, saw seven roles, selected zero, and timed out. Geography, low scores, and stale or mismatched official destinations accounted for the rejects. A listing category cannot replace employer verification. The per-source configuration and broader fit/yield review remain open.
- The generic browser runner no longer calls a one-page result exhaustive merely because it saw no visible Next link. It now requires evidence that it followed pagination before marking a later terminal page exhausted; one-page and infinite-scroll coverage remains partial/unknown. A three-origin, one-request-each HTTP check of broader category pages returned 200 without challenge, but static HTML did not establish complete pagination or candidate suitability. This is not yet the paced browser shadow required by 4.2.
- Automatic title-and-company suppression has been removed. Distinct official ATS IDs remain separate, while weak-only matches against prior active applications are visible and held before an automatic final action. Generic URL identity confidence and the broader state model remain open in 2.1/2.1a.
- A private live audit found multiple recent verified receipts at one employer despite distinct official role IDs. The branch now keeps another role visible but requires exact review after two recent verified receipts at one employer, and rechecks the threshold before automatic final permit commit. This is an application-quality hold, not a search exclusion.
- A private operational baseline now records the two 50-source campaign IDs, start/end times, source-health totals, and zero receipts. The durable campaign summary did not expose exact query filters or a full deployed Git hash; 0.1 remains open until those are recovered or explicitly recorded as unavailable in the measurement contract. Stored opportunities omit rejected source rows, so they cannot substitute for the 100-case quality holdout.
- The workflow report now separates campaign wall time per verified receipt from median/p95 first-observed-to-receipt latency and reports stage sample counts. It also requires an observed discovery request before marking a campaign as a fresh timing sample, so an imported preselected lead cannot create a false end-to-end timing claim. Full stage attribution, source coverage, and the live pilot remain open in 3.3/4.4.
- The source funnel now joins campaign applications to each reported discovery source once, exposing requested, attempted, and verified-receipt counts. Missing source identity is reported as unattributed rather than silently credited to a provider. This is partial 3.1/3.2; full stage attribution and live reconciliation remain open.
- Unresolved destination listings remain retriable, and a later verified destination can update the same stored role. Primary adapter rows with unverified direct employer URLs enter this pending lane too; they do not consume actionable slots or become handled merely by observation. Pending leads use bounded backoff and a seven-day observation TTL. Worker-confirmed unavailable postings enter a closed state with bounded backoff and require a fresh matching official ATS role to reopen. Repeated-campaign, cross-source, receipt, and uncertain-final-action regressions cover these transitions. The broader 2.1 state contract and arbitrary employer-page verification in 2.2 remain open.
- Himalayas and Jobicy direct/short same-board redirects to official Ashby, Greenhouse, or Lever roles now receive a fresh official role fetch, re-scoring, location check, stable-ID dedup, bounded candidate/request budget, 1.5-second same-origin pacing, and 403/429 backoff before becoming actionable. Non-ATS employer pages and conflicting or unavailable official roles stay pending/excluded. This is partial 2.2: arbitrary employer-page identity/form verification remains open, and no live yield claim is made from fixtures.
- Himalayas' official feed exposes description text. A narrow additional path recognizes exactly one explicit role-specific ATS URL following “Apply here,” then requires a fresh official role, exact title/company match, and the existing geography, pacing, and cooldown gates. Ambiguous or mismatched links remain pending. Jobicy's public feed does not provide an equivalent supported direct-link field, so its non-ATS links remain pending.
