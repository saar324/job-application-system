# Standing submission authorization

The default remains exact final-preview approval. An agent bearer token cannot enable automatic submission by changing profile preferences. The owner must use a credential whose authenticated identity has the `owner` role and `PUT /v1/standing-submission-policy`. `GET` on the same route is profile-bound and available to the agent. A policy has an ID and increasing version; setting `mode: "always"` revokes automatic submission. A fresh owner mutation is required to re-enable it. Previously pending final approvals stay pending.

The owner policy explicitly names modes, source IDs, destination hosts, answer classes, and daily and campaign caps. It does not relax job fit rules, employer-site limits, or hard holds. Legal attestations require manual review because ordinary saved answers are agent-writable and cannot prove owner consent. Agent-provided application answers and unverified site prefill also hold at the final gate. Required unknown answers, account challenges, employer AI restrictions, and uncertain prior final actions follow the worker's existing hold paths.

Automatic submission requires a recent opportunity created by a server-fetched discovery adapter with a verified employer application destination. Caller-supplied source, score, `userRequested`, and discovery-verification fields never establish this status. Direct links and browser-imported fallback candidates use exact approval. The server re-scores a verified role against the current profile at intake and final review; an expired or more than ten-minute-old discovery verification holds it for a fresh scan. The browser still checks that the actual application form is present. Legal holds include work authorization, visa, sponsorship, and right-to-work questions even if the mode's optional confirmation list omits them.

The worker sends the observed final preview and fingerprint to the server's `/v1/internal/final-decision` route using the worker shared secret. A covering owner policy produces a 30-second permit, reserved against the caps. Immediately before the click the worker calls `/v1/internal/final-commit`; the server rereads the policy and checks version, revocation, fingerprint, and caps. An unavailable or rejected callback holds the form. A revocation can still occur in the network-to-click interval after commit; commit is the authorization point, and this system does not claim zero race beyond it. Revoking policy blocks permits that have not yet committed.

The worker requires `JOB_SERVER_INTERNAL_URL` pointing to the local job server. The production environment splitter and updater pass `http://127.0.0.1:4310`; the worker rejects non-local callback URLs. The server uses `APPLICATION_WEBHOOK_TOKEN` for its internal callback route and the worker uses its matching `WORKER_TOKEN`. Do not put either token in a profile or application payload.

The cap counts receipts plus reserved and committed final actions, rather than intake records. Unused reservations expire after 30 seconds. A committed action with uncertain outcome conservatively keeps its cap slot until reconciliation so it cannot be silently retried.

The profile write atomically stores a bounded owner policy history entry with each version. The separate application-state audit is idempotent and secondary. If that audit write fails, the owner API still reports the durable policy mutation as successful, avoiding an ambiguous retry that would create another version.
