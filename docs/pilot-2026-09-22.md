# Live application pilot, 22 September 2026

## Scope and result

The target was ten new, eligible applications processed sequentially with the upgraded worker. The pilot did not reach ten submissions. Four distinct employer applications entered the server: one reached a complete final preview, two await factual or human form action, and one employer posting had closed. No final Submit action was taken, so the verified submission count is zero.

These are attempts, not submissions. The server's final-preview and receipt gates behaved as intended. We did not repeat a prior submission or count a board listing as an application.

## Measurements

- Bounded Himalayas search: 287 listing results, 33 passed source-level qualification, and 254 were excluded. The official configured-source scan returned 208 listing results, with nine passing source-level qualification. These counts may overlap and are not counts of distinct eligible jobs.
- ElevenLabs was queued at 11:35:09 UTC and reached its final preview at about 11:37:26 UTC. This is roughly 2 minutes 17 seconds of elapsed form preparation and answer resolution. The first six questions required fact checking or writing; browser execution took only seconds.
- Aggregate server metrics after the pilot work: queue median 465 ms (13 samples); execution median 2.4 s, p95 23.4 s (25 attempts); worker active median 3.4 s, p95 22.8 s (10 samples). These are cumulative metrics, not an isolated ten-application sample. The attempt count includes retries during fault repair.
- Model and coordinator token counters are unavailable (`null`). We cannot claim token savings from this pilot.
- The user's former estimate of 100 applications in eight hours is a reference point, not a verified baseline. With one complete preview and no submissions, there is no defensible post-upgrade throughput comparison yet.

## Defects found and fixed

The live Xebia form exposed two worker defects. A public reCAPTCHA iframe was treated as a forbidden top-level destination, and a passive invisible reCAPTCHA badge was treated as an active human challenge before safe form fields were filled. The worker now checks the application-host allowlist for top-level navigations, still validates public DNS on every request, fills safe controls before challenge detection, and pauses only for an interactive challenge. Regression tests cover both cases. Commit `269758f` was deployed to the production worker. The full check passed: 156 tests and the repository privacy gate.

## Next bottlenecks

1. **Candidate supply and deduplication.** Many high-fit listings are already submitted, rejected, or stale in the application history. Board searches frequently return old or geographically ineligible roles. Before preparing a form, verify the official employer posting and compare employer role IDs against the application log.
2. **Known-answer reuse.** The ElevenLabs worker requested GitHub and LinkedIn links already present in the saved profile. Composite labels such as “Link to your Github or profile” need safe deterministic mappings. Reuse employer-scoped and previously confirmed prose carefully; do not treat unreviewed historical drafts as owner facts.
3. **Custom form scoping.** Intetics presents multiple forms on one page. A provider adapter or stronger application-form selection could identify the correct controls; the CAPTCHA remains a human step.
4. **Coordinator telemetry.** Time spent finding, deduplicating, verifying, and writing applications is not measured by `application-metrics`. Add stage timing and token counts before claiming end-to-end speed gains.

Continue only with verified, eligible, unapplied roles. Exact completed previews need owner approval before submission. Unknown legal or personal facts require owner answers, and CAPTCHAs require human action.
