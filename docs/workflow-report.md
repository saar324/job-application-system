# Campaign workflow trace

Run `jobctl campaign-report CAMPAIGN_ID` or `GET /v1/campaigns/CAMPAIGN_ID/workflow-report` with the profile's bearer token. The response uses durable `workflow.stage` events in the application state. Events contain UTC timestamps, stage names, IDs, counts, and measured durations. They do not contain form answers, names, email addresses, job text, URLs, or document paths.

`elapsedWallMs` runs from campaign creation to its terminal timestamp, or to the report time while it is active. `activeWorkerMs` sums only measured worker active time; it is `null` when no worker supplied a measurement. Resolved owner waits and still-open owner waits are separate. These durations can overlap and should not be added to reconstruct wall time. Discovery fetch, screening, and employer-destination durations use a monotonic clock and are recorded with their source yield. Browser preparation, drafting, transition, and receipt timings remain available in attempt metrics when the worker provides them.

For automatic standing-policy submissions, `final_action` records the server permit consumption immediately before the worker click. For older exact-approval submissions, the trace records `inferred_from_receipt` when a verified receipt arrives; its timestamp is the receipt time, not a measured click time.

`counts.newVerified` requires a non-simulated, non-manual production-adapter receipt with a submission timestamp and final URL. Manual receipts and simulations are reported separately. `attemptedApplications`, total attempts, handled listings, blocked, skipped, rejected, and failed records are separate counts. Duplicates consume discovery work but do not increase `newVerified`. `sourceYield` shows found, qualifying, excluded, handled, destination-pending, and selected counts for each source.
`sourceHealth` adds each source's terminal diagnosis, request/page counts where measured, and official-feed exclusion
categories. A zero-extractable browser result is not proof that the site has no open jobs.

`measurementKind: fresh_campaign` means the campaign has a recorded source scan and none of its selected opportunities predates the campaign. If candidates came from a preloaded reserve or acquisition is incomplete, the report says `preloaded_or_incomplete` and `endToEndEligible: false`. For preloaded roles, `reserve.attributableMaintenanceMs` and `observedMaintenanceRequests` show available refresh evidence from the official-source refresh or browser reserve campaign. Missing maintenance measurements stay `null`. These fields disclose upstream work; they do not turn a preloaded run into a fresh end-to-end result. `target100InOneHourProven` remains false until the later live acceptance gate is implemented and passed.

Model call count is complete only when every attempt reports `draftCalls`; otherwise `modelCalls` is `null`, with a separate observed partial count and sample count. Browser steps follow the same complete/partial rule. Worker active time follows it too. Model input/output tokens, coordinator tokens, and total tool calls remain `null` because the current providers do not supply those measurements. Legacy campaigns can have empty stage traces and unknown values; the report does not turn missing measurements into zero.
