## Timing

The first application record was created at 06:41:24 UTC. The seventh receipt was recorded at 09:58:09 UTC: **196.75
minutes** elapsed, including preparation, review, owner approval, worker failures, browser recovery, and duplicate
reconciliation. That is **28.11 minutes per verified submission**; a straight-line 100-submission estimate is **46.85
hours** if this mix repeats. After batch approval at 08:57:27 UTC, the seven receipts took **60.70 minutes**, or **8.67
minutes per verified submission**. Neither figure meets the 30-second target, and neither is a controlled browser-speed
benchmark.

## Failure analysis and correction

The staging headless worker completed Enode but received Ashby spam rejections or uncertain outcomes on most other forms.
Regular Chrome produced explicit success for the remaining successful Ashby forms. This is a browser-environment
reliability problem, not evidence that the form filling itself is slow. The regular-browser fallback required substantial
manual coordination.

The duplicate filter missed an Ashby role when one URL ended in `/application` and another did not, and missed a
Greenhouse role previously discovered through Himalayas because the old application's employer confirmation URL was not
indexed. The branch now matches stable ATS role IDs across listing and application URLs and indexes verified receipt URLs
for discovery and direct intake. Tests cover both regressions. This correction is on the isolated branch; production is
unchanged until rollout and live verification.

The next acceptance run must start with three genuinely new, suitable roles and a complete exact approval review. It must
record source coverage, application preparation, owner wait, browser active time, and receipts separately. The current
seven receipts must not be counted again.
