# Discovery coverage and application quality rollout

This guide accompanies [the OpenSpec change](../openspec/changes/restore-discovery-coverage-and-pilot-accounting/proposal.md). It describes the draft implementation and the evidence needed before promotion. A passing fixture suite is not a completed ten-application pilot.

## Search behavior

The service screens a bounded pool of up to 500 roles per official ATS source query and 200 per public-board query, filters handled stable role identities, scores the remaining roles, ranks them, and retains at most `limitPerSource` accepted roles per source. Himalayas and Arbeitnow follow bounded pages; Jobicy processes the provider's unpaginated 200-row response per term. Source reports distinguish a provider cap or partial failure from exhaustion. The browser Jobgether adapter keeps a cursor for each query variant and reports later pages before claiming completion. A manual or cooling source is covered operationally but is not exhausted.

Lexical sources use a three-cycle title plan seeded from configured preferences and verified submitted titles. Each plan reserves a broad software probe when the profile has software-role intent. Historical titles affect retrieval only; the normal role scorer decides eligibility. The service saves per-profile source cycle ordinals in campaign state. The all-source runner writes the browser query seed to a private temporary file, deletes it after the browser process exits, and never puts contact fields into that seed. `--query-plan-file` and `--search-cycle` are available for a controlled rerun.

The browser runner can rotate through up to eight reviewed role-listing URLs configured for each source. Every URL must remain on the catalog URL's HTTPS origin. The public repository stores no applicant-specific board selection; the private source catalog supplies the pages after a source-specific review. The existing page, request, and time limits still apply. A live paced shadow is required to measure actual yield and employer fit for each configured source.

The generic browser runner treats a first page without a visible Next link as partial coverage because static HTML does not prove a dynamic or infinite-scroll board is exhausted. A later page reached through a visible Next link can establish the end of that pagination path. A bounded static-HTML check returned HTTP 200 without challenge for three reviewed category pages, but it did not verify browser-rendered pagination or candidate suitability.

The first bounded shadow of a broader browser listing took 35 seconds and nine requests. It observed seven roles, selected none, and timed out after one listing page. Six roles had incompatible geography, and one scored below the automatic minimum.

A second listing shadow also took 35 seconds and nine requests, observed seven roles, selected none, and timed out after one listing page. The employer check rejected three stale or mismatched ATS destinations; three other roles had incompatible geography; one scored below the automatic minimum. A listing category cannot replace employer verification. The source remains measured low-yield and partial-coverage evidence.

Provider requests remain capped. The browser scanner stops a source on 403/429 or challenge; adapter failures are surfaced as partial source errors. A source with an unknown provider total is not reported as comprehensively exhausted. `sourceCoverage.coveredCount` counts attempted/terminal reporting, while the workflow report's `coverage.exhaustive` requires every planned source to have an explicit exhausted result.

Himalayas documents its `country` search parameter as an eligibility filter for jobs a resident may take, including worldwide matches unless `exclude_worldwide` is set. The adapter leaves `exclude_worldwide` unset by default. This supports using the profile's residence country for that source; other browser sources still need their geography filters audited individually. See the [Himalayas API reference](https://himalayas.app/docs/remote-jobs-api) and [location guidance](https://himalayas.app/docs/how-to-get-a-remote-job).

Greenhouse remote evidence distinguishes an onsite work requirement from optional onsite team events. A current Europe posting explicitly offering fully remote work was previously rejected because it also mentioned onsite team events. The verifier now permits that combination while still rejecting actual hybrid and onsite work requirements.

The Greenhouse feed and current official role detail now expose compensation only when the employer text clearly labels an annual salary range with an ISO currency. The normal pay-floor gate then uses that range. Unlabeled money, ambiguous periods, and conflicting ranges stay unknown; the parser does not infer gross/net basis or convert currencies.

When a file control is rescanned during final review, the worker checks the live submit form for one file with the recorded filename and byte size. A lost, empty, changed-size, or ambiguous upload still pauses. This addresses a live résumé readback pause without accepting a vanished attachment as evidence of upload.

The source funnel now exposes observed raw rows, adapter prescreen rejects, deduped rows, handled rows, scored rows, qualified rows, destination-pending rows, pages, requests, per-term yield, skipped terms, and partial reasons where the provider supplies the data. A missing raw or page count remains `null`, not zero. Browser candidates are written to a private per-campaign journal before reporting. A failed report is retried after restart using the same idempotency key; manual and cooldown paths record discarded candidate count and reason. A browser-observed employer URL outside a directly checked ATS remains pending until current role identity and form availability are independently verified.

The campaign report joins each durable application back to its discovery source to show requested applications, attempted applications, and verified receipts per source. Applications without a matching reported source appear in a separate unattributed count, so source totals reconcile without assigning a receipt to a guessed source.

Distinct openings at one employer stay visible. After two verified receipts to that employer within 30 days, another application enters exact review rather than automatic submission. A fresh receipt arriving between final permit and commit also stops the automatic action. This protects application quality without treating company name alone as a duplicate role ID.

Himalayas and Jobicy links that point directly to Ashby, Greenhouse, or Lever, or reach one through at most three HTTPS redirects on the aggregator's own host, now receive a fresh official ATS lookup before selection. The official row supplies role identity, title, location, remote status, and destination for scoring and deduplication. Non-ATS links remain pending. New official lookups have a ten-candidate source cap, the existing request budget, 1.5-second spacing per origin, and cooldown on 403/429. This resolves only the supported official ATS subset of the pending-link gap; it does not verify arbitrary employer pages.

Himalayas description text can additionally name an explicit “Apply here” official ATS URL. The importer uses it only when it is the sole role-specific ATS URL and a fresh official lookup matches the listing title and company. This route keeps the same request and geography guards. Jobicy's public feed does not expose a supported direct employer link, so description links there remain pending.

Primary adapter rows with a direct employer URL but no verified official role now enter the pending lane too. They cannot use a ready slot or become a handled role merely because the URL was observed. A later discovery pass can revisit them, and pending-to-ready promotion requires verified destination evidence. This closes a path where an unverified link could previously be selected as actionable.

Pending links use a 30-minute exponential retry delay capped at 24 hours and expire after seven days of unresolved observation. A worker-confirmed unavailable posting enters a separate closed state, with a 24-hour retry delay capped at seven days. A closed lead can reopen only after a fresh matching official ATS verification, and a receipt or uncertain final action continues to block another submission. The source report counts deferred leads separately from handled roles.

A read-only Himalayas shadow after this change used 25 requests in 21 seconds. It observed 392 raw rows, normalized 200, found seven qualifying but still unresolved board links, and produced **zero employer-verified ready roles**. The raw pool and official-verification request caps were both partial; the result is not source exhaustion. A separate single listing-page GET returned HTTP 403, so that page path was not retried or used as verification evidence. This source still needs a supported employer-link route and a later bounded retest.

## Applicant evidence and prose

An owner can register verified examples with `PUT /v1/profile/verified-examples` using `{ "examples": [...] }`. Each record requires an ID, one to five exact facts, a source kind and reference, scope (`employer`, `roleTerms`, or `skillTerms`), and `reviewAfter` within 90 days. `GET` is owner-only and profile scoped. Ordinary profile `PATCH` cannot create these records. The worker receives at most four current, relevant examples in `evidencePacket.applicant.examples`; drafts cite them as `applicant:example:<id>`.

Prose drafted by `WORKER_DRAFT_ENDPOINT` requires an independent claim reviewer before it is filled. Configure `WORKER_CLAIM_REVIEW_ENABLED=true` and `WORKER_CLAIM_REVIEW_ENDPOINT` on a different endpoint from the draft provider; token and timeout variables are optional. The reviewer must return `supported`, `responsive`, `companySpecific`, and a nonempty `claims` array with each claim's exact text from the draft, support decision, and evidence IDs. Unsupported or unresponsive drafts stop for correction; company motivation without a concrete employer fact stops for research. If the reviewer is absent or unavailable, the worker holds new prose for manual review. Legal, work-authorization, compensation, and demographic answers remain separate owner facts, not model-generated prose.

Previously approved motivation or experience prose now requires exact role scope for reuse; a same-employer answer without it is not reused. Changing verified applicant examples invalidates prior answer evidence fingerprints. A reused approved answer is classified as `grounded_prose` at the standing-policy final permit, so a policy that authorizes only profile facts cannot submit it. Every final action still uses the existing form-value readback, standing policy, and receipt checks.

If the employer form says an answer must be human-written or prohibits AI, even a role-scoped approved answer pauses for exact human-authorship review. Stored approval alone does not prove the answer meets that employer's writing instruction.

## Evaluation and promotion

The private baseline captured on September 24 has 30 development and 100 holdout role cases, separated before ranking changes. It combines stored opportunities with live raw official ATS listings. Stored opportunities omit rejected provider rows; the live sample covers only selected configured ATS boards. Two blinded reviewers must rate role fit and adjudicate disagreements. A separate question/answer set must cover employer-specific motivation, optional high-value questions, unsupported personal examples, and same-employer/different-role reuse. Do not interpret a role-fit label as proof of prose quality.

Promotion requires zero critical unsupported applicant claims, legal errors, duplicate final actions, or false receipts; nonworse paired median role fit and prose quality; and at most a five percentage point drop in cases rated at least 4/5 on the 100-case holdout. Then run a one-lane shadow search, inspect newly included/rejected/unresolved roles and employer geography, deploy source by source with rollback, and audit ten real submitted applications. The throughput denominator is new verified employer receipts. With zero receipts, time per application and a 100-application forecast are unavailable.

The September 24 production campaigns produced zero verified receipts. Their 50 planned sources had timeouts, cooldowns, manual sources, unresolved destinations, and unknown provider totals, so those runs do not establish exhaustive coverage or a speed result. The private operational report retains the exact timestamps and source breakdown without committing applicant data.

## September 24 shadow result

A reserve-only, production-state-seeded shadow campaign attempted and terminally reported all 50 configured sources. It took **14 minutes 17 seconds** and made **260 provider requests**. Only **17 sources reported exhaustion**. The other statuses included 15 timeouts, four rate limits, three partial errors, three response/page caps, one manual source, and unresolved destinations. It produced **zero verified employer receipts**. The two initially surfaced browser leads did not survive employer evidence review; the branch now holds such unverified employer links as pending.

An independent read-only review of 20 strong but excluded or uncertain roles found **one current official role ready for manual fit review**, six unresolved, and 13 rejected. Applicant fit and compensation policy still need confirmation for that role. This is evidence of a supply and screening bottleneck, not a measured application throughput improvement. No ten-application timing or 100-application forecast is available.

The frozen 100-case role holdout and 30-case development set have two blinded fit reviews and an adjudication file. The stored historical scores are not a valid paired old/new path comparison because the old scorer and profile context differ. No blinded paired application-answer review, configured independent claim reviewer, or ten-receipt pilot exists yet. Keep this change in draft and do not deploy automatic broader submission until the paired quality gate passes.

A separate private application-question corpus is now frozen: 30 development cases and 100 holdout cases with no employer overlap. It stores references and hashes rather than historical answer text. The sample covers motivation, personal examples, same-employer/different-role reuse risks, and a small number of optional-question candidates. Historical answers are not verified applicant facts; optional requiredness and answer approval dates are unavailable. Only three development cases and five holdout cases have at least 100 characters of stored role description. The corpus supplies a stable sample, but the missing evidence and draft/review provider prevent a valid paired old/new prose-quality comparison. A production configuration check found no enabled draft or independent claim-review endpoint, so unresolved prose still requires manual handling.

An official ATS board can be hosted by a recruiting intermediary while the description names a different hiring company. A narrow signal detects an explicit opening sentence of the form “Role Company is a software company” when the board's configured company differs. It routes the role to employer-identity review and prevents covered automatic intake until reviewed; it does not infer which company is correct. This pattern occurs once in the frozen development roles and not in the holdout, so further live audit is needed. A separate public-board listing was also observed for an official role with an existing receipt. Treat the official role identity and receipt as handled even if the public-board record has a different ID; that cross-source regression remains open.

A bounded advisory fit-review lane now samples lower-scored roles across sources without itself authorizing automatic submission. A location correction also keeps a remote role eligible for scoring when its hiring-region list includes both an accepted and an excluded alternative; an excluded-only location still stops it. In a paired simulation on the frozen role cases, review surfaced 13 of 15 suitable holdout roles rejected by the automatic gate, versus five before; eight of ten suitable roles below 60 points without hard exclusions reached review, versus zero before. The review queue grew from ten to 20 cases; automatic selection was unchanged on these cases. These figures measure review visibility on stored cases, not live retrieval or final application quality. A human or evidence-based reviewer still has to decide whether each surfaced role is suitable.

The production configuration behind that shadow has nine Ashby boards, eight Greenhouse boards, and two Lever sites. These three source names therefore cover 19 configured company boards; they do not search every employer on those ATS platforms. Independent official-posting checks found several relevant boards outside that inventory, while many apparent matches were already handled. Board expansion needs a bounded, profile-scoped provenance and refresh policy before its yield can be counted as systematic coverage.

The branch now learns at most five extra boards per ATS source from this profile's own official-role verifications or non-simulated submission receipts within 30 days. It rotates these boards across completed source cycles, excludes active board cooldowns, and records the seed provenance. Configured boards remain first. Same-origin ATS requests are paced and queued requests stop after 403/429. Every new posting still passes current handled-role and suitability checks; a historical receipt only extends retrieval. This cannot discover never-observed employers, so the broader board-inventory task remains open.

A read-only Ashby check seeded one recently verified official role into a copied profile state. The source fetched all nine configured Ashby boards plus one learned board in **15 seconds**, with **10/10 allowed requests**, at least **1.5 seconds** between same-origin requests, and no HTTP or rate-limit errors. It observed 175 raw rows: four adapter prescreen rejects, 27 previously handled roles, 144 scored roles, 112 hard exclusions, 32 roles held for opportunistic requirements, and **zero new eligible unhandled roles**. This confirms the learned-board fetch and pacing path. It does not establish broader employer coverage or faster verified applications; the shadow state did not submit anything.

Two further read-only Ashby cycles used the same copied profile state and up to five rotating historical boards in each cycle. Each fetched 14 boards in about **20 seconds** with no HTTP errors. Under the then-current 200-role cap, the cycles observed 169 and 200 candidate roles, respectively, and selected **zero new eligible unhandled roles**. The second hit that cap, so it was partial coverage. These results verify the rotation and pacing mechanism; they do not establish a supply increase or submission speed.

A read-only Greenhouse cycle fetched 13 boards in about **20 seconds**. With the wider 500-role scoring pool, it scored 428 unhandled roles with no response cap and selected **zero**. A Lever cycle fetched seven boards in about **11 seconds**, scored 62 roles, and selected **zero**. There were no HTTP errors. An evidence review of eight Greenhouse fit-review candidates promoted none: the current employer requirements depended on specializations, language, or management evidence absent from the verified applicant record. The detailed role judgments remain in the private operational report. These cycles show the current bottleneck is verified fit and role supply, not a form-filling time measurement.

A separate bounded browser-source cycle after the main shadow used five listing pages and 16 requests over 60 seconds. It observed ten extracted roles: seven excluded, one handled, one verified official ATS selection, and one employer link pending verification. It timed out before exhaustion. The production server verified and opened that one preselected form. It paused on two mandatory written answers that explicitly prohibit AI-written text. Earlier history contains topic notes, not the applicant's original wording. This preselected form cannot be used as a fresh end-to-end throughput sample, and it has no receipt yet. Employer and applicant details remain in the private operational report.

The next bounded browser-source query rotation took **60 seconds**, visited five listing pages, and made 17 requests. It found 11 extracted roles and two newly observed employer links, both still pending employer evidence; it selected **zero** verified ready roles and timed out before exhaustion. Manual review found a required framework absent from verified applicant evidence for one role and unresolved employer-role identity and geography for the other. Neither is promoted into the application lane.

A paced Jobgether geography probe compared the first 25 full-remote software-search results with and without the `locations=europe` filter. Both requests returned HTTP 200 and more pages; their first-page role IDs did not overlap. The filtered page used broad Europe/Anywhere labels, while the unfiltered page included several country-specific listings. Those country labels alone do not establish that this applicant can work there, so the probe does not justify removing the eligibility filter or promoting any role. It does show that the filter changes the candidate pool; source-specific geography behavior remains open for a deeper employer-eligibility audit.
