# Two search workers, one application session

Read this reference for a search-and-apply session or an explicitly assigned search-worker role. The main chat owns the applicant queue's current form. It starts exactly two search subagents, `search-1` and `search-2`, using the collaboration tools. These agents discover, review, prepare tentative answer packets and append jobs only. They never claim an application for execution, insert data into employer forms, upload files, access accounts, submit, send email, skip queued jobs, change applicant facts or alter source settings. Preparation leases are passive draft ownership only. Do not resurrect retired server campaigns or form workers.

## Main session

1. Recover the current application first. Read health, fit context, configured sources, known jobs and `search-status`. Use the real parent chat ID for `sessionId` in every search operation, including child operations. Source and application ownership remain separate.
2. Build the ordered source IDs from the private catalog's `autonomousDiscovery.priorityOrder`. Resolve IDs against its configured adapter/browser sources. Exclude manual-only, user-controlled, disabled, reserved and direct-outreach entries. When the private catalog is empty, use the public starter and available server sources. Prefer the saved source ranking; do not invent yield measurements. Do not reset the priority list merely because one source had a poor page. Source suitability is independent of truthful job-level country/stack review.
3. Call `search-start` with `{sessionId, mode, sources:[ordered IDs]}`. The server persists this plan per authenticated applicant and main chat. A different main chat must stop the old search session explicitly after its agents have stopped before taking over. Never steal a live source. Changing source order or mode also requires stopping both agents first.
4. Call `search-control` with `{sessionId}` to persist the 20/30 buffer decision. Count only pending queue items, excluding the current form, holds and completed jobs. At 20 or fewer, begin one refill cycle. Continue at 21 to 29 until 30 is reached. At 30 or more, stop the two workers and keep the source plan and cursors. Check control at session recovery, after claiming or completing each application, and after owner links or worker updates. New jobs append to the bottom. Do not reset or trim older entries. The server cannot spawn Codex agents itself.
5. Spawn the two agents with the worker prompt below and the parent ID. Use a fresh short context (`fork_turns:"none"`) so application credentials and private form answers are not copied unnecessarily. Record the returned agent IDs in this main chat. Reuse them with follow-up tasks rather than repeatedly spawning new agents. If collaboration capacity is unavailable, keep applying and report the missing worker; do not pretend two workers are active.
6. Work on the existing FIFO application queue while both agents search. The agents can append passive jobs during a CAPTCHA or missing-fact hold; this never clears the blocker or opens another form. The main chat stops application work and asks only for the current blocker. Agents cannot ask the owner questions or interfere with the form. This search-only exception supersedes the earlier rule stopping all discovery during an application hold.
7. Workers run bounded passes and return progress to the main chat. Resume the same two idle workers only when `buffer.shouldStartWorkers` is true. At the high watermark, workers release sources with `paused` and return. Keep the session active for the next low watermark cycle. If a bounded pass ends below 30 and good sources remain, continue it. If every source is blocked or has no good remaining matches, report that limitation without lowering quality or busy polling. Read their updates between forms. Do not busy-poll a completed daily pass. Keep the owner's target and daily submission cap separate from queued counts; weak matches do not satisfy a target.
8. Every new Europe/Sofia calendar day, the server reopens sources in the saved priority order and resets that day's cursors/quality counters on the next operation. Live leases survive midnight until released or expired, so resetting does not assign a source twice. Application/handled-role history and receipts remain intact. Resume the same two workers for the new daily pass. This is an active-session workflow, not an overnight daemon or an automation; no new schedule is created.
9. If the owner ends or pauses search, interrupt both workers, wait for their current requests to finish, then `search-stop`. Stop and reclaim old workers before replacing one. Do not run a replacement alongside a stalled agent. When setup is requested without an active search request, install the workflow without starting live discovery.

## Worker prompt

Send a self-contained message with actual paths and IDs substituted:

> You are search worker WORKER_ID for main chat PARENT_CHAT_ID. Read BASE_DIR/references/search-workers.md, BASE_DIR/references/applicant-facts.md, the configured sources catalog, and the current server fit context. Use node BASE_DIR/scripts/jobctl.js. Use `draft-context` once for verified facts and their fingerprint. You may search public jobs, review fit, prepare JSON suggestions and append passive work through search-* operations. Read BASE_DIR/references/application-drafts.md. Check buffer control before source work and after every enqueue. First use exclusive preparation leases to backfill older pending jobs while the refill cycle is active. Do not spawn agents or insert data in application forms, use accounts or execute submissions. Read public form questions through public sources when available. If questions are inaccessible or gated, record incomplete observation and generic suggestions instead of logging in or bypassing the gate. Do not change configuration. Use PARENT_CHAT_ID as sessionId and WORKER_ID as workerId. Claim an exclusive source, respect its limits, browse only its relevant public inventory, review each full official posting, filter known roles and enqueue relevant unseen jobs. Preserve partial-stack matches and the owner's country-specific remote/B2B instruction; do not invent qualifications or location eligibility. Report progress to the main agent. Do not ask the owner. Stop on access challenges for that source and move to the next lease. Return when the buffer reaches 30 or no good sources are available. A bounded pass can return progress but does not end an unfinished refill cycle. Do not label a bounded pass as market exhaustion.

## Worker loop and commands

All mutation payloads are JSON on standard input. `search-status` is a read. Lease IDs are coordination identifiers, not credentials.

- `search-control`: `{sessionId}`. Returns durable low/high watermarks, pending count, refill cycle and `shouldStartWorkers` / `shouldStopWorkers`. Workers must not search while `shouldSearch` is false. The atomic enqueue guard also prevents two workers from crossing 30.
- `search-prepare-claim`: `{sessionId,workerId}`. Exclusively leases the oldest undrafted or stale pending job during a refill cycle, without claiming its form. Renew the same lease with this call during longer preparation. `search-prepare-save` takes `{sessionId,workerId,leaseId,applicationId,profileFingerprint,draft}`. It saves suggestions only. A main-session claim or expired lease rejects the write. Backfill does not reorder the queue or consume a submission attempt.
- `search-claim`: `{sessionId,workerId}`. Returns the highest-ranked available source and a lease `{id,sourceId,workerId,day,expiresAt,cursor}`. The same worker retains its current assignment. There are exactly two worker slots. Never select another source independently or continue a source without a valid lease.
- `search-progress`: `{sessionId,workerId,leaseId,reviewed:0,strongMatches:0,duplicates:0,pageComplete:false,cursor:null}`. Call before each source request and at least every five minutes. Leases expire after 20 minutes without renewal. Counts describe one newly reviewed page, not lifetime totals. A heartbeat uses zero counts and `pageComplete:false`. Save a non-secret page URL/provider cursor. Never save auth URLs, tokens, private profile data or codes. Stop using results if lease validation fails.
- Prefer `search-scan` with `{sessionId,workerId,leaseId,scan:{reviewOnly:true,limitPerSource:20}}` for configured feeds, or `search-query` with a bounded provider query plan. The server fixes the source and mode to the lease and preserves shared request quotas. These routes remain search-only even while the application is held. For public browser boards, use independent public web retrieval/search; never share or navigate the main application's browser tab or its persistent browser REPL. If the source requires login, manual browsing or an access challenge, mark this source blocked for the daily pass and move on. LinkedIn stays owner-controlled.
- Use `filter` to remove known roles before expensive official-posting reviews. Read the complete current official job text; an aggregator summary or search snippet alone is insufficient. Evaluate core responsibilities, remote work, compensation and verified experience. Country-restricted remote roles and a partial stack are not automatic exclusions when the owner has authorized them. Save accurate uncertainty and cross-border contract disclosure for the main session to use later.
- `search-enqueue`: `{sessionId,workerId,leaseId,officialPostingReviewed:true,profileFingerprint,draft:STRUCTURED_PACKET,candidate:{source:LEASE_SOURCE_ID,title,company,description,applyUrl,listingUrl,remote,location,...},fit:{decision:"relevant",reason:"Evidence-based review"}}`. Use the full official posting as description and its official destination. The server reviews/records the role and atomically appends it with a validated tentative draft packet through the existing deduplicating queue. Use the current `draft-context` fingerprint. A profile correction requires reloading context and checking suggestions before retrying. Never use `queue-add` with a discovered URL: that path marks it owner-supplied. Inspect the returned status. `review_official_posting` requires reviewing the returned official text before retry; unverified or filtered jobs are not queued. Unsupported official destinations can queue after this explicit full-posting review; the main chat must recheck the live form.
- Finish a source with `search-finish`: `{sessionId,workerId,leaseId,outcome,reason}`. `low_quality` requires two focused result pages without an unseen strong match. Continue a productive source while it yields good matches. `pass_complete` means the bounded current inventory/search pass ended, not global exhaustion. `blocked` records an access restriction, 403/429, login or challenge; never bypass it. `paused` releases the lease while keeping its saved cursor available for a later same-day pass. Claim the next highest-ranked available source immediately after finishing.
- Duplicate-heavy, stale or irrelevant pages count as poor pages; never lower fit quality merely to keep a source productive. An HTTP failure is a block, not evidence of zero jobs. If the source returns no lease, report daily pass complete or busy sources and return; the main chat can resume later.

Only the main chat uses `queue-next`, checkpoint, resume, review, final-action and receipt commands. Existing profile-bound deduplication, current-form ownership, consent gates and receipt counting stay in force. Queued jobs are not applications sent.

## Draft handoff

Every new discovered job includes the single JSON packet specified in [application-drafts.md](application-drafts.md). It contains exact observed questions when available, tentative values, provenance, role research, cover letter or motivation prose, and explicit unknowns. Do not promote these suggestions to applicant facts or consent. The main chat loads the whole packet, corrects it before insertion, maps it to the actual live form and verifies insertion. Workers never ask the owner or touch the main browser.
